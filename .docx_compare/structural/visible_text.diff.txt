 [Heading1] 7  Discussion
 [Heading2] 7.1 Answering the research questions
-[Normal] RQ1: configuration with human oversight. EasyRTG breaks configuration into structural checks, relative calibration, and reward writing against an approved vocabulary. Compiling and auditing occur automatically before any tool runs. Users do not edit the underlying environment source code at all. A comparative user study measuring time savings has not yet been conducted.
-[Normal] RQ2: applicability across robot bodies. Treating morphology and state terms as dimensionless values allows one pipeline to generate viable policies for the A1, ANYmal, and Go1 quadrupeds alongside the Valkyrie humanoid. This approach removes fixed geometric constraints that typically constrain standard simulation pipelines. The test results confirm it functions correctly across these specific URDF models. It cannot however support manipulators or wheeled robots without significant architectural changes.
-[Normal] RQ3: differences between learners. All three algorithms produced nearly identical performance caps when controlling the Go1 quadruped. PPO, SAC, and TD3 showed negligible variance in final reward values within that specific environment. The Valkyrie results tell a different story entirely. SAC became the only viable option for that platform while neither PPO nor TD3 achieved stable gait patterns. Uneven algorithm coverage and incomplete hyperparameter tuning weaken these conclusions.
-[Normal] RQ4: simulation throughput. Parallel environments allowed throughput to scale until robot physics created a hard ceiling. A single GPU processed 32,056 steps per second across 4,096 environments for the A1 configuration. Valkyrie performed below that threshold due to increased rigid-body solver latency from its mass and joint count. These figures align with the architectural shifts toward Isaac detailed in Section 5.2, which matches GPU simulation benchmarks published by Castano [10] and Garcia [13].
+[Heading2] RQ1: With human supervision configuration. EasyRTG splits configuration up into: structural checks, relative calibration and writing rewards on a ratified word stock. Compiling and auditing is performed automatically, prior to any tool running. The user does not modify in any way the source code of the underlying environment. A comparative user study, measurement of time savings, has not yet been conducted.
+[Heading2] RQ2: applicability with respect to robot bodies.  [Heading2] 8.1 Conclusion
-[Normal] This work establishes an integrated desktop platform enabling users to import a URDF robot, define a locomotion task in natural language, and train reinforcement learning policies without writing low-level simulator scripts. All five primary objectives outlined in Chapter 1 were satisfied.
-[Normal] The system relies on a Flutter frontend, a FastAPI-orchestrated backend, PyBullet-based parameter inspection, and training within the NVIDIA Isaac Sim simulator using GPU hardware to autonomously extract motion physics directly from the URDF tree. Rewards are captured and audited as evaluated mathematical expressions via an established vocabulary facilitated by an LLM operating under strictly confined user validation protocols. The complete application underwent analysis across thirty-four Isaac Sim runs utilising four distinct robot families and three continuous-control algorithms.
-[Normal] Three significant outcomes defined the experimental trials. Parallel execution on the GPU eliminated the CPU bottleneck for multi-platform learning, achieving a peak throughput of 32,056.8 environment steps per second at a single workstation level using an RTX 5000 GPU. For quadruped models such as the Go1, learner selection exerted minimally significant influence over final outcomes; PPO, SAC, and TD3 achieved greater than ninety-six percent survival episodes and converged upon comparable reward scores. Conversely, algorithm choice directly dictated training viability on higher-dimensional platforms like the Valkyrie humanoid. SAC emerged as the solitary method maintaining stable balance throughout its simulation, reaching an eighty-two point one percent survival score while PPO and TD3 plateaued at twenty percent, with TD3 subsequently degrading into numerical instability.
-[Normal] The engineering process was fundamentally driven by mitigating failures encountered during iterative integration. Initial challenges necessitated the inclusion of robot-relative floor-falling terminations, while fragile rule-based naming conventions were discarded in favour of a robust kinematic tree traversal mechanism. Directories and safety concerns regarding arbitrary Python execution mandated an AST expression compiler, whereas galloping traversal conditions informed the explicit modelling of foot surface contact states within Isaac Sim.
-[Normal] A notable limitation arose during the Go1 galloping test, where imprecise reward specifications drove TD3 to emulate a rapid trot movement. This unintended locomotion mode accumulated exceptionally high scalar rewards, causing the platform to entirely omit required airtime during its motion phase. The experiment confirms that unconstrained total reward volumes serve insufficiently as indicators of actual movement behaviour; without monitoring contact signals, episode length, and preliminary videos, unregulated reward accumulation remains practically insignificant. Finally, while the internal AI assistant frequently achieved functional reward functions from natural language inputs, it nonetheless requires a significantly expanded validation set to guarantee robustness in complex engineering scenarios.
-[Normal] The application evolved from its initial CPU-based conceptualisation into a fully operational pipeline. This progression demonstrates that robotic locomotion, reward design, and GPU-assisted training can be consolidated into a single no-code desktop platform while maintaining strict user oversight.
+[Heading2] This work brings together an integrated desktop platform for taking in one URDF robot file and outputting one locomotion task in natural language, and for training RL policies directly without having to write low level simulator scripts.
